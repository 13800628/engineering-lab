# permission-bits

## 目的

Goのビット演算(`|`, `&`, `&^`, `^`, シフト)で、Unix風の9bit権限を操作する。
状態をJSONに永続化し、読み込み時の検証で「外部入力を信用しない」設計も確認する。

## 技術・バージョン

- 言語/ランタイム: Go 1.27(2026年8月リリース。パッチ番号は `go version` で確認)
- ビルドツール: Go modules(`go.mod` は実験フォルダ直下、他ディレクトリへの依存なし)
- 主要ライブラリ: 標準ライブラリのみ(`encoding/json`, `os`, `fmt`, `strings`, `sort`, `errors`)

## 選定理由

- Goには「ビットクリア」専用の演算子 `&^` があり、on(OR)・off(AND NOT)・flip(XOR)・can(AND)の4演算が揃う。ビット演算の学習題材に向いている。
- 他の候補(C、Rustなど)でも同じ演算は書ける。ただしCはメモリ管理やビルド周りの本筋でない部分に気を取られやすく、`&^` のような演算子もない。今回はビット演算とJSON検証に集中するため、そして言語慣れがあるGoにした。
- `os.FileMode` は使わず、`uint16` ベースの自前型で権限を持つ。`FileMode` が内部でやっていることを自分で書いて理解するため。
- 外部ライブラリ(CLIフレームワークなど)は使わない。引数分岐は `os.Args` と `map` だけで足りる最小実装にした。

## 構成

```
tools/permission-bits-go/
├── go.mod         # モジュール定義(go 1.27)
├── main.go        # コマンド分岐、引数の個数チェック、エラー表示と終了コード
├── permission.go  # Permission型、ビット定数(iota+シフト)、各ビット演算、表示用変換
└── store.go       # state.json の読み書きと、読み込み時の検証
```

- 状態ファイル `state.json` は、実行時のカレントディレクトリに作られる(パスは `store.go` の定数 `stateFilePath`)。

## 実行方法

```bash
cd tools/permission-bits-go
go build -o perm .

./perm create hello.txt
./perm set hello.txt 110100100
./perm show hello.txt
./perm on|off|flip|can hello.txt <bit名>
```

- コマンド形式: `perm <subcommand> <filename> [argument]`
- ビット名: `owner-r` `owner-w` `owner-x` `group-r` `group-w` `group-x` `other-r` `other-w` `other-x`
- エラー(存在しないファイル、不正なビット名、不正な9bit文字列、state.json の検証失敗)は、メッセージを出して終了コード1になる。
- ポート番号などは無い(CLIのみ)。

## 学習ポイント

- **ビット定数の定義(`permission.go`)**: `1 << iota` で、ビットが1つだけ立った値が自動で並ぶ仕組み。2行目以降で式を省略できる理由と、Other→Owner の順に並べる理由(文字列の左端が最上位ビットになる)。
- **on / off / flip / can と演算の対応**:
  - on = OR: 他のビットを変えずに狙ったビットだけ立てる。
  - off = `&^`: 狙ったビットだけ0にする。`p & (^bit)` と同じ。
  - flip = XOR: 狙ったビットだけ反転する。2回やると元に戻る。
  - can = AND: 狙ったビットだけ取り出し、0かどうかで判定する(マスク)。
- **9bit文字列 ↔ 数値の変換**: 1文字ずつ左シフトしながら取り込む `ParseBits` と、上位ビットから `(p >> i) & 1` で取り出す `BitString`。
- **show の変換(シフトとマスク)**: 8進数は3bitずつ `(p >> 6) & 0b111` のように切り出す。rwx表記は、3bitのうち4・2・1の各ビットを `r`・`w`・`x` に対応させる。
- **読み込み時の検証と「外部入力を信用しない」理由**:
  - state.json は手で編集でき、書き込み中の障害でも壊れる。
  - 範囲外の値を通すと、9bitの前提が崩れて表示や演算が静かにおかしくなる。
  - 読み込みの時点で止めれば、壊れたデータが後続に広がらず、元のファイルも上書きされない。
  - 欠落の検出にポインタ型を使う理由、`uint16` へのキャスト前に範囲を検証する理由もあわせて確認する。

## 結果・気づき

- ビット演算の部分を正しく実装することの大切さ、ここがないとどの形であれど正しく変換されることがない。
- 3ビット単位での処理によってユーザーごとでの権限操作を正しく行う。そして9ビットとして受け取るのでそれを互いに干渉ないように気をつけることも大切
- bitをうまく活用してパーミッションは作られているのだなと感じた。(9という数値を3者で3役持たせるというのが他の機能作る際にも抽象化して活用できそう)
